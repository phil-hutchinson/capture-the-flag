# Peer Review — 00000029 Measure speed during training

## Summary

The branch adds a game-agnostic, call-path-nested cumulative timer
(`capture_the_flag/instrumentation/`), instruments every seam this repository
owns (position mechanics, the learned evaluator and its decode phases, the
network forward pass and mode switch, the boundary into `MCTSEngine`, and the
training orchestrator's generation split), and leaves each run a
`timings.json`/`timings.txt` pair carrying settings, environment, and the tree.
A seeded benchmark measures the instrumentation's own cost, and the resulting
"on by default" decision, the measurement recipe, and the findings from a
full-scale run are written up in the story folder. The design is careful and
unusually well documented, the region-per-call rule from the plan is respected
throughout, and coverage of the story's acceptance criteria is close to
complete.

Static checks at review time, from the repository root: **`pyright` — 0 errors, 0
warnings, 0 informations**; **`ruff check .` — all checks passed**. The default
test suite passed (313 passed, 15 deselected). The `slow` suite did **not**:
`pytest -m slow tests/instrumentation` failed on two of three attempts (see issue
1) — the failure was in the test, not in the production code, but the branch as
delivered had a red slow suite.

The implementation plan does include a README review step (Step 10), and the
README was updated accordingly, so no comment is raised on that.

**Status after resolution.** All twelve items are addressed; see each row's
Resolution. Re-checked afterwards: `pyright` 0 errors, `ruff` clean, 318 fast
tests pass, all 16 slow tests pass, and `pytest -m slow tests/instrumentation`
passed on three consecutive runs. Two behavioural changes are worth knowing about
beyond the code: a training run now rewrites its record at every checkpoint (so an
interrupted run leaves what it finished), and a batch writing into a directory
that already holds a record now writes `timings-2` rather than replacing it.
